# Local persistence

Dicta stores metrics and settings in a versioned SQLite database. The initial schema migration is `user_version = 1`; timestamps are normalized to UTC RFC 3339 and SQLite indexes session start time, language, and model. The frontend receives snake_case JSON types from `domain/mod.rs`. SQLite `secure_delete` is enabled, and privacy deletions, retention purges, and full metric clears checkpoint and truncate the WAL after commit. Checkpoints wait up to five seconds for other database readers; if one remains active, the repository returns an error instead of claiming the disk purge completed. This protects normal SQLite files, not copies in backups, filesystem snapshots, or SSD wear-leveling storage.

Transcripts are stored in a separate table only when `history_enabled` is true. This defaults to false. Saving settings with history disabled deletes every stored transcript in the same transaction as the setting change; writes with history disabled also remove any transcript for that session. Clearing transcript history leaves metrics intact. Clearing metrics removes the related session rows, so their transcripts are removed by the foreign-key cascade as well. Recovery text belongs to the caller's in-memory state and is never part of this repository API.

`save_session` accepts both in-progress and terminal states. At startup, `recover_interrupted` changes any unfinished session into a failed session with `error_category = "interrupted"`. The session row remains useful for counts and timing, and its transcript is unaffected unless history is disabled. Retention is measured against each session's UTC start time and is applied when settings are saved. The configured period is limited to 1–3650 days.

The word count is supplied by the dictation pipeline and uses whitespace-delimited tokens containing at least one Unicode alphanumeric character; this layer persists the count and does not infer it from transcript text. Without history opt-in, metrics contain only counts, timings, model/language labels, input mode, and error category. Do not put transcript content or audio in errors or metric fields.

Dashboard filters use local inclusive calendar dates. SQL `localtime` conversion supplies timeline buckets, weekday/hour heatmaps, and active-day counts, so SQLite applies the host's daylight-saving rules to each UTC timestamp. The DST test inserts two UTC instants near the 2024-03-31 transition, then checks the SQL heatmap hours against each instant converted through the process's local timezone, and checks the timeline count. It verifies SQLite/Chrono agreement for the configured host timezone; it does not force a timezone or claim coverage for every timezone database rule. `week` starts Monday. A custom start or end date overrides the corresponding rolling-window boundary; otherwise the window ends today locally and spans `days` inclusive. Filters are parameterized. Search treats `%`, `_`, and `\` literally. Results are newest first and limited to 1–500 rows; search is capped at 256 bytes.

Inference mean, median, and p95 use completed sessions only. Median and p95 are calculated from the ordered inference-duration values because SQLite's built-in aggregate set does not provide portable percentile functions; all filtering and session aggregation remain in SQLite. The median averages the two middle durations for even-sized sets; p95 uses nearest-rank selection. WPM is stored words divided by recorded audio minutes; throughput is recorded audio time divided by inference time. Zero denominators produce zero. Word-change percentage is `null` when the previous period has no words. Histogram bins are `0-30s`, `30-60s`, `1-3m`, and `3m+`.

Exports return file contents to the caller for a user-initiated local save. CSV fields are quoted and embedded quotes doubled; formula-like text cells get a leading apostrophe to reduce spreadsheet formula injection risk. Transcript exports include only rows that exist in the opt-in transcript table. No encryption is applied to this local SQLite database; applications should rely on OS account and disk protections and communicate that choice in privacy settings.

## Synthetic query smoke benchmark

On Apple M4 / macOS 26.6 with optimized Rust and rusqlite 0.40.2, one in-memory run inserted 10,000 synthetic sessions through `save_session` in 135 ms; a 90-day `dashboard` query returned in 51 ms. Rows were distributed across 89 dates, two languages and two models, with completed/cancelled statuses; no transcript text was stored. This is a local query smoke check, not a production workload or a latency guarantee. It excludes app startup, disk I/O, and UI rendering, and it was a single run rather than a statistical benchmark.
